# Swiss QR Bill on Invoice PDFs — Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.
>
> **Status 2026-10-04: Tasks 1–5 implemented.** Remaining: the manual bank verification at the end of Task 5 (scan a real PDF, make a test payment) — that cannot be automated.

**Goal:** Every invoice PDF carries a standards-compliant Swiss QR bill (payment part, 210 × 105 mm, bottom of the last page) with a per-invoice structured reference, so clients can pay by scanning and incoming payments can be matched back to the invoice.

**Architecture:** A new `App\Actions\Invoice\QrBill` action builds and validates a `Sprain\SwissQrBill\QrBill` from the invoice, the client and `config/invoice.php`, and returns the payment part as HTML. `resources/views/pdf/invoice.blade.php` renders it on a final full-bleed page.

**Tech Stack:** `sprain/swiss-qr-bill` v3.3 (already installed, currently unused), `endroid/qr-code` (installed), Spatie Laravel PDF + Browsershot (headless Chrome), Laravel 12 Action pattern.

## Decisions (locked with user)

- **Account: `CH22 8080 8003 1865 2284 6`** (Raiffeisenbank Weinland) — the account the invoice PDF already prints. Holder is **Marcel Stadelmann**, matching `beneficiary_name`, so the QR bill's creditor name is correct as-is.
- **Reference type: SCOR** (ISO 11649 creditor reference, `RF…`), generated from the invoice number. **No QR-IBAN, no BESR-ID, no bank setup required** — this is what unblocks the whole feature.
- The unused `qr_iban` / `classic_iban` config entries are **removed**; neither is the live account and keeping them invites picking the wrong one.

Nothing else in this plan moves. A QR-IBAN buys stronger ESR-style reconciliation in camt.054; SCOR still carries the reference structurally.

## Standards constraints that shape the code

- **Structured addresses only.** Combined addresses (type `K`) are no longer permitted under current SIX guidelines. Use `StructuredAddress::createWithStreet(...)` for creditor *and* debtor — `sprain` v3.3 still accepts `CombinedAddress` without a violation, so **validation will not catch this for us**.
- **Payment part geometry is fixed:** 210 × 105 mm, flush with the bottom edge of the last page, no margins, perforation line included. The main technical hurdle (Task 3).
- `AdditionalInformation` ≤ 140 characters.
- Amount must be > 0 (or omitted) and ≤ 999 999 999.99; currency CHF or EUR only.
- Always generate the reference with `RfCreditorReferenceGenerator` — never hand-roll the check digits.

## Open question — still needs an answer, does not block Tasks 1–2

**Print the debtor ("Zahlbar durch"), or leave it blank?** Filling it requires a country code per client, which the `clients` table does not store (`name, acronym, byline, street, zip, city, publish`). Leaving the field blank is standards-compliant and the client writes it in; filling it looks more finished but costs a migration + a form field. **Recommendation: leave blank for v1**, since the invoice already addresses the client at the top of the page.

### Task 2 — `App\Actions\Invoice\QrBill` ✅

```php
public function execute(Invoice $invoice): string    // payment part HTML
public function reference(Invoice $invoice): string  // RF… from the invoice number
```

- Creditor: `StructuredAddress::createWithStreet()` from config; creditor information from `config('invoice.iban')` (spaces stripped).
- `PaymentAmountInformation::create(config('invoice.currency'), $invoice->grandtotal)`.
- `PaymentReference::create(TYPE_SCOR, RfCreditorReferenceGenerator::generate($numberWithoutDot))`.
- `AdditionalInformation` = `"Rechnung {$number}"` / `"{$level}. Mahnung zur Rechnung {$number}"`, truncated to 140.
- Debtor omitted for v1 (see open question).
- **Throw on violations**, surfacing `getPropertyPath()` — a silently malformed bill is worse than a failed render.
- Output via `HtmlOutput($qrBill, 'de')->setPrintable(false)->getPaymentPart()`.
- **Skip the QR bill entirely for cancelled invoices** (amount 0 — nothing to pay).

### Task 3 — Fit the payment part into the PDF ✅ *(route B, after a measured spike)*

`App\Actions\Pdf\Build` renders with `->margins(30, 20, 30, 20)` plus Chrome header/footer templates (`pdf.partials.header` / `footer`) that apply to **every** page — including the one the QR bill lands on, where they would overprint it.

- **(A) Overlay — small change, lower fidelity.** Keep current margins; the payment part gets an opaque white background and bleeds out with negative margins. Risk: Chrome clips to the content box, so the bleed may not reach the physical edge and the footer may show through.
- **(B) CSS-driven page layout — bigger change, correct result (recommended).** Browsershot margins to `0`, move page margins into CSS padding on the invoice content, re-implement header/footer as `position: fixed` repeating elements, suppressed on the QR page. The QR page is then genuinely full-bleed and exact.

**What the spike established (all measured against rendered PDFs at 150 dpi):**

- Browsershot's explicit `->margins()` **override CSS named pages**, so route A could never go full-bleed. With Browsershot at `margins(0,0,0,0)`, CSS `@page` margins *are* honoured, including a named `@page qrpage { margin: 0 }`.
- Chrome's **native** header/footer composite on top of page content, so an opaque element cannot mask them. CSS `position: fixed` runners *can* be masked this way — which is how the footer is kept out of the payment part.
- `position: fixed` repeats on every printed page, positioned against the page **content box**. Negative offsets to reach into the margin are unreliable and were abandoned.
- `height: 100%` on the layout table resolves against the whole document, not a page, so it only pinned the footer on single-page invoices. The footer is therefore a fixed runner, with `tfoot` left as a 20 mm spacer that reserves the band on every page.
- The payment part's natural height is **105.4 mm**, not 105 mm. Pinning the wrapper to exactly `105mm` overflows by a fraction and breaks it onto an extra page — the wrapper must size to its content.

**Final shape:** `@page { margin: 10mm 20mm }` + `@page qrpage { margin: 0 }`; the logo lives in a repeating `thead` (20 mm) and the address strip is a fixed runner at `bottom: 0`; the QR page sits outside the layout table.

**Measured result** — single-page and multi-page invoices both verified:

| | baseline | after |
|---|---|---|
| content top / bottom / left | 10.2 / 286.7 / 19.8 mm | 10.0 / 286.6 / 20.0 mm |
| QR page width | — | 210.1 mm (full bleed) |
| QR page bottom edge | — | 297.0 mm (flush) |

On a 2-page invoice both content pages now measure identically, with the logo and footer repeating on each.

### Task 4 — Wire it up, clean out the dead route ✅

- Render the payment part in `resources/views/pdf/invoice.blade.php`; **remove the "Bankverbindung" box** once the QR bill ships (the payment part already states account, beneficiary, reference and amount — keeping both risks them disagreeing).
